# บันทึกการเรียนรู้ของโครงงาน slideqr-seg

สรุปสั้น ๆ หลังจบแต่ละขั้น ว่าทำอะไร ทำไม และได้ผลอะไร ให้เพื่อนร่วมทีมอ่านตามได้
ตัวเลขทุกตัวในไฟล์นี้มาจาก **ภาพสังเคราะห์** จนกว่าจะทดสอบกับภาพจริง

---

## ขั้นที่ 1 ตัวสร้างภาพสังเคราะห์

**ทำอะไร**
- เขียนโปรแกรมวาดฉากสไลด์ชิ้นเนื้อ 1 ถึง 10 แผ่นเรียงแถวเดียว แต่ละแผ่นมีฉลากและรหัส 2 มิติ
  (DataMatrix 18x18 ขนาด 6.5 มม. เป็นค่าเริ่ม รองรับ QR 21 ด้วย)
- พื้นหลังสุ่ม 5 แบบ: ฐาน PLA (แท่นจริงที่จะใช้), ถาดสเตนเลส, ถาดพลาสติก, โต๊ะ, กระดาษหรือแฟ้ม
  ชนิดพื้นหลังบันทึกลง `metadata.csv` เพื่อดูภายหลังว่าพื้นหลังแบบไหนทำให้โมเดลพลาด
- กล้อง 2 โหมด: `rig` มองตรงลงจากสะพานกลางแถว (ชุดหลัก) และ `handheld` ถ่ายเฉียง (ชุดทดสอบความทนทาน)
- ความเสื่อมของภาพ เช่น แสงสะท้อน เบลอ noise JPEG เปิดปิดและปรับแรงได้ทีละตัวใน config
- ส่งออกป้ายกำกับทั้ง YOLO และ COCO พร้อม `metadata.csv` หนึ่งแถวต่อรหัส

**ทำไม**
- ป้ายกำกับต้องแม่นระดับมุมของรหัส การวาดเองทำให้รู้มุมจริงทุกจุดโดยไม่ต้องให้คนหรือโมเดลติดป้าย
- วาดทุกวัตถุในหน่วยมิลลิเมตรแล้วฉายผ่านกล้องจำลองครั้งเดียว มุมที่บันทึกจึงตรงกับภาพระดับต่ำกว่า 1 พิกเซล
- สุ่มพิกเซลต่อ module (ppm) 2 ถึง 8 เพื่อหาจุดที่ระบบเริ่มอ่านไม่ออก ซึ่งใช้ตัดสินใจเลือกกล้อง

**ได้ผลอะไร**
- ทดสอบภาพสะอาด (ยังไม่ใส่ความเสื่อม): ถอดรหัสได้ 100% ทุกช่วง ppm, bit error เป็น 0
  และค่าความคลาดเมื่อเลื่อนมุม 0.5 px สูงกว่ามุมจริงทุกช่วง แปลว่ามุมแม่นระดับ sub-pixel
- ตรวจ layout แบบสุ่ม 5000 แบบ ไม่พบฉลากอยู่ผิดปลาย ไม่พบสไลด์ซ้อนกันหรือเอียงเกินกำหนด
- ชุดข้อมูลเต็ม: train 2100, val 450, test (rig) 450, test_handheld 600 ภาพ รวม 19,506 รหัส
  แบ่ง split ตาม ppm ให้แต่ละชุดมีสัดส่วน ppm เท่ากัน
- ตารางเลือกกล้อง (`docs/camera_table.md`): บนฐาน PLA กล้องต้องเห็นทั้งกรอบ 300 มม.
  กล้อง 8MP ได้ประมาณ 3.8 ppm และ 12MP ได้ประมาณ 4.7 ppm (ค่าทางเรขาคณิต ของจริงต่ำกว่านี้)

**บทเรียน**
- ข้อจำกัดทางกายภาพสำคัญ: ภาพกว้าง 3264 px เห็น 10 แผ่นพร้อมกันได้ที่ ppm ไม่เกินราว 4
- เจอบั๊กหลายจุดจากการตรวจภาพจริงทีละภาพ เช่น กล้องเล็งไปที่ช่องว่าง, การแบ่ง split ที่ทำให้ชุดเล็กไม่มี test
  การทดสอบที่ตั้งใจป้อนข้อมูลผิดเพื่อดูว่าตัวตรวจจับได้จริง ช่วยให้มั่นใจกว่าการดูว่าผ่าน

## ขั้นที่ 2 เตรียมเครื่องและเทรน 4 โมเดล

**ทำอะไร**
- ย้ายการเทรนไปใน WSL2 Ubuntu 24.04 บนเครื่องเดิม ใช้การ์ด RTX 5070 ตัวเดิม
- เปลี่ยนฟอนต์บนฉลากเป็น DejaVu ที่ติดตั้งผ่าน apt
- เทรน Mask R-CNN, YOLO11n-seg, YOLO26n-seg และ RF-DETR-Seg Nano ด้วยเงื่อนไขเดียวกัน:
  ข้อมูลชุดเดียวกัน, ภาพด้านยาว 1280 px, งบเวลาเทรนเท่ากัน 60 นาทีต่อโมเดล (รวมเวลา validation), seed เดียวกัน

**ทำไม**
- บน Windows เครื่องนี้ Smart App Control บล็อกไฟล์ `torch.dll` จึงโหลด PyTorch ไม่ได้
  WSL2 ใช้ PyTorch ฉบับ Linux และไม่ต้องปิดระบบป้องกันของเครื่อง
- ข้อมูลเก็บในระบบไฟล์ของ Ubuntu (`~/slideqr-seg/data`) เพราะการอ่านไฟล์เล็กจำนวนมากผ่าน `/mnt/c` ช้ามาก
- ฟอนต์ Windows แจกต่อไม่ได้และแต่ละเครื่องไม่เหมือนกัน DejaVu ฟรี ทุกคนสร้างภาพได้ตรงกัน
- งบเวลาเท่ากันยุติธรรมกว่าจำนวน epoch เท่ากัน เพราะแต่ละโมเดลเร็วไม่เท่ากัน

**ได้ผลอะไร**
- PyTorch 2.11 cu128 ทำงานบน sm_120 ใน WSL ได้
- ก่อนเทรนจริงได้ทดสอบทุกโมเดลด้วยข้อมูลชุดเล็กและงบ 2 นาที เจอปัญหาและแก้แล้ว (รายละเอียดใน README):
  - RF-DETR ต้องติดตั้งส่วนเสริมสำหรับเทรน และความละเอียดต้องหาร 12 ลงตัว จึงใช้ 1272 แทน 1280
  - RF-DETR batch 2 ใช้หน่วยความจำเกิน 12 GB จึงใช้ batch 1 สะสม gradient 8 รอบ (effective batch 8)
  - **บั๊กสำคัญ:** RF-DETR คืนเลขคลาสเริ่มจาก 0 ไม่ใช่เลขของ COCO ถ้าไม่ตรวจ สไลด์จะถูกนับเป็นรหัสทั้งหมด
    จับได้เพราะผลแปลก (AP มีค่าแต่ตรวจพบ 0%) แล้วไปดูขนาด mask ที่ทำนายออกมา
  - การวัดเวลาครั้งแรกปน CPU กับ GPU จนได้ค่าเท่ากัน จึงแยกวัดเวลาเฉพาะโมเดลกับเวลาทั้งระบบ

**บทเรียน**
- ทดสอบทั้งสายงานด้วยข้อมูลชุดเล็กก่อนเทรนจริงหลายชั่วโมง ประหยัดเวลามาก
- ผลที่ดูแปลกต้องหาสาเหตุก่อนเชื่อ บั๊ก RF-DETR ข้างบนจะทำให้สรุปผิดว่าโมเดลแย่

(ผลการเทรนและการวัดผลจะเพิ่มในขั้นที่ 3)
